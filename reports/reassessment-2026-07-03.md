## Confirmed bugs

### 1. (New, low-medium impact) Three accessibility gaps in the new `StopDetail` UI — same recurring "missing ARIA affordance" class this repo has shipped repeatedly (aria-pressed, 07-01/07-02)
- `src/components/StopDetail.tsx:26-30` — the loading `Skeleton` is a bare `<div aria-label=... />` with no `role`. Without `role="status"` (or similar), most assistive tech ignores a naked `aria-label` on a non-interactive `<div>`, so screen-reader users get no "loading" announcement at all while sights/safety/packing sections are pending.
- `src/components/StopDetail.tsx:114-125` — the fetch-failure error banner (with its Retry button) has no `role="alert"`/`aria-live`. It appears asynchronously after the initial render, so a screen-reader user has no indication a failure occurred unless they happen to re-scan the region.
- `src/components/StopsSection.tsx:100-104` — the expand/collapse toggle sets `aria-expanded` but has no `aria-controls` pointing at the `StopDetail` panel's id, and the panel itself has no `id`, so the expanded-content relationship isn't programmatically associated for AT users.

None of these break functionality for sighted/mouse users; all are genuine a11y regressions in newly-shipped code, in the same bug family CLAUDE.md's QA norms already ask reviewers to watch for.

## Improvement opportunities

- **Tombstone the trip-delete sync path.** `mergeTrips` (`src/lib/supabase/trips.ts:138-162`) unions local+remote by id with no delete-awareness; a failed `deleteRemoteTrip` can still resurrect a trip on next merge. The failure is now surfaced (SyncBadge), but the actual fix — a `deleted_at`/tombstone column or client-side deleted-id allowlist — is still open. Worth scheduling now that it's the last unresolved item from two cycles of the same bug family.
- **Fix the three `StopDetail` a11y gaps above** (`role="status"` on `Skeleton`, `role="alert"` on the error banner, `aria-controls`/`id` linking the toggle to the panel) — small, contained fixes, same shape as the `aria-pressed` fixes from 07-01.
- **Clean up the 9 orphaned `ADVISORY` keys** in `src/data/advisories.ts`, or leave a comment noting they're intentional pre-coverage for destinations not yet in the dataset — as-is it's ambiguous whether it's dead data or forward-planning.
- `advisoryDot()` (`src/data/advisories.ts:83-85`) is exported but has zero importers anywhere in `src/` — `SafetyNote.tsx` intentionally inlines its own copy of the same dot map instead (commented as a deliberate bundle-hygiene choice, `SafetyNote.tsx:1-3`), which is reasonable, but that leaves `advisoryDot` itself dead. Low priority; delete or use it server-side.
- The implementation plan's own status note flags "region page adopts the route" as deferred — `/regions/[id]` (`src/app/regions/[id]/page.tsx`) still has its own direct-import data path rather than going through `/api/region-detail`, meaning the sights/toolkit/advisory-rendering logic now exists in two places. Not a bug (the direct import is fine server-side), but worth eventually consolidating so future data-shape changes don't need to be made twice.
