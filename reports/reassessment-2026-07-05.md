## Confirmed bugs

### 1. (New, medium impact) Editor-invite email enumeration is only half-fixed — the "Current editors" list refresh leaks the same fact the new RPC was built to hide
`src/components/InviteEditorDialog.tsx:43-63` (`invite()`), backed by `src/lib/supabase/collaborate.ts:9-21` and `supabase/schema.sql:150-183`.

This cycle's `1faca84` deliberately replaced the old `getUserIdByEmail` lookup — which told the inviter outright whether an email had an account — with `invite_trip_editor_by_email`, a `security definer` function whose own comment says it exists "without revealing whether that email has an account," and whose client wrapper (`inviteEditorByEmail`) always returns the same generic `{error: undefined}` regardless of whether the email matched a user, matched the caller themselves, or was already invited. The dialog now shows a single non-committal message either way: *"Invite sent. If that email has an account, they'll be added."*

But `invite()` immediately re-fetches `listEditors(tripId, ownerId)` after every invite attempt (`InviteEditorDialog.tsx:58-60`) and re-renders the "Current editors" list with it. Since the RPC only inserts a `trip_editors` row when the email actually resolves to a real, distinct account, the inviter can trivially tell the two cases apart without reading any special-cased text: submit an email, and see whether the editors list grew by one. This is exactly the oracle the RPC redesign and its comment say the feature should not have. The old code's explicit "No account found" message was a more blatant version of the same leak; this cycle fixed the explicit message but not the underlying side channel.

Fix is narrow: don't auto-refresh `listEditors` after a successful invite (the existing code already has a comment rationalizing *not* refreshing on partial failure — the same reasoning applies here), or delay/batch the refresh so it isn't attributable to a single invite attempt.
